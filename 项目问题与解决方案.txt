一、GPU 显存与硬件瓶颈
================================================================================

问题 1.1：RTX 4060 8GB VRAM 不足以同时运行 CARLA + BEVFormer
  现象：1280x960 分辨率下 GPU 利用率 0%（完全卡死），显存占用 95%（7820 MiB）
  根因：8 路高分辨率摄像头渲染 + BEVFormer-tiny 推理合计超出 8GB 物理限制
  解决：将所有 8 路摄像头分辨率从 1280x960 降至 640x480（像素量减少 75%）
  效果：GPU 利用率从 0% 恢复至 70%，温度从 50°C 升至 58°C（活跃工作）
  文件：tesla_camera_layout.py（所有 8 路摄像头 width/height 修改）
  局限：BEVFormer 输入质量降低，但作为 Surrogate 模型的相对比较仍然有效

问题 1.2：CARLA 低画质模式无法根本解决 VRAM 瓶颈
  现象：CarlaUE4.exe -quality-level=Low 使 CARLA 渲染显存从 786MB 降至 224MB
  但总 VRAM 仍 95%
  结论：低画质只能部分缓解，无法根本解决 8GB VRAM 瓶颈
  最终方案：保持 640x480 分辨率 + 低画质 CARLA 启动的协同优化

问题 1.3：无法运行 BEVFormer-base/small 更大模型
  现象：BEVFormer-base 需 28.5GB VRAM，small 需 10.5GB，均超出硬件限制
  影响：只能运行 tiny 版本（BEV 50x50, ResNet-50 backbone）
  缓解：Phase 4 考虑模型蒸馏或量化；以相对变化量评估攻击效果

二、CARLA 仿真器稳定性问题
================================================================================

问题 2.1：长时程实验中 CARLA 服务端偶发超时
  现象：连续运行 >30 分钟后，world.tick() 超时（130s+）
  触发条件：GPU 温度 >60°C，显存饱和
  缓解：重启 CARLA 服务端 + 低画质模式
  代码实现：collect_baseline.py 内置卡死自愈机制（传送重置 + post_reset 标记）

问题 2.2：同步模式下 spawn 摄像头导致死锁
  现象：先启用 synchronous mode 再 spawn 车辆和摄像头时，world.tick() 超时
  根因：同步模式下 actor spawn 需要 tick 驱动，但 tick 需要所有 actor 就绪，形成死锁
  解决：在异步模式下完成所有 actor spawn，sleep(1.0) 等待就绪，最后启用 synchronous mode
  规则：spawn -> sleep(1.0) -> enable_sync -> route_loop -> disable_sync -> cleanup

问题 2.3：world.load_world() 重载地图导致卡死
  现象：在线模式中使用 load_world('Town10HD_Opt') 重载地图耗时且可能导致服务端卡死
  解决：使用 client.get_world() 获取当前世界，不重载地图

问题 2.4：CARLA 0.9.16 无独立 TrafficManager 可执行文件
  现象：尝试启动 TrafficManager.exe --port 8000 失败
  根因：CARLA 0.9.16 的 Traffic Manager 集成于 Python API 中
  解决：使用 set_autopilot() 时 TM 自动启动，端口 8000

三、摄像头与传感器配置问题
================================================================================

问题 3.1：CARLA 摄像头物理朝向与配置值相反（侧视/后视）
  现象：|yaw|>=45° 的摄像头（侧视/后视）实际朝向与配置值相反
  根因：CARLA 将子 actor 的旋转相对父 actor 应用
  解决：在 spawn_tesla_cameras() 和 build_img_metas() 中对 |yaw|>=45° 取反 yaw
  注意：前视摄像头（yaw=0°/+5°）不受影响，保持原值

问题 3.2：全局 euler_to_rotation yaw 取反方案失败
  现象：在 euler_to_rotation() 中全局取反 yaw，导致前视摄像头 lidar2cam 矩阵错误
  根因：前视摄像头 yaw 接近 0°，取反后投影关系被破坏
  解决：仅在 spawn 和 build_img_metas 中对 |yaw|>=45° 条件取反，保持前视不受影响

问题 3.3：摄像头回调重复 attach 导致 CARLA 超时
  现象：每条路线在 run_one_route_reuse 中 attach 回调，重复 attach 导致服务端超时
  解决：回调在 main() 中 attach 一次，frame_buffer 跨路线共享

问题 3.4：每帧清空 frame buffer 导致大量帧被跳过
  现象：清空 buffer 后部分摄像头来不及在新 tick 内写入数据，大量帧因"不足 8 路"被跳过
  根因：摄像头回调是异步的，清空后数据写入有延迟
  解决：累积模式 -- 保留每个摄像头的最新帧，不清空 buffer
  配合：预热期 5 帧 + sleep(0.2s)/帧，等待所有摄像头回调就绪

问题 3.5：阴性对照实验异常（非 BEV 消费摄像头仍有响应）
  现象：攻击 front_narrow / side_rear_right（不在 BEV 消费链路内）仍有检测响应
  可能原因：攻击通过空间注意力机制间接影响其他摄像头
  状态：待进一步验证

四、BEVFormer 模型适配问题
================================================================================

问题 4.1：img_metas 批次维度与摄像头数量混淆
  现象：extract_img_feat 在 B=1 时 squeeze 掉批次维度，导致 num_cams(6) 被误认为 batch_size
  解决：img_metas 复制 6 份，确保维度正确

问题 4.2：box_type_3d 设置错误导致 get_bboxes 报错
  现象：box_type_3d 设为字符串时，get_bboxes 内部类型检查失败
  解决：必须设为 LiDARInstance3DBoxes 类对象（非字符串）

问题 4.3：mmdet3d v0.17.1 模块双重注册
  现象：mmcv.utils.Registry 中模块被注册两次，抛出 RuntimeError
  解决：monkey-patch mmcv.utils.Registry._register_module 解决双重注册

问题 4.4：numba 版本兼容性（numba>=0.53 移除 numba.errors）
  现象：BEVFormer 依赖的 numba.errors 模块在新版本中不存在
  解决：创建 numba.errors 伪模块（import numba.errors; numba.errors = numba）

问题 4.5：BEVFormer 源码导入错误（dd3d、tkinter、v2 数据集）
  现象：projects/mmdet3d_plugin 导入 dd3d 相关模块时报错
  解决：手动修改 4 个源码文件：
    - projects/mmdet3d_plugin/__init__.py -- 注释 dd3d 导入
    - projects/mmdet3d_plugin/datasets/__init__.py -- 注释 v2 数据集导入
    - projects/mmdet3d_plugin/datasets/pipelines/__init__.py -- 注释 dd3d_mapper 导入
    - projects/mmdet3d_plugin/bevformer/detectors/bevformer_fp16.py -- 删除 tkinter 导入

问题 4.6：BEV 时序缓存无法启用
  现象：尝试启用 prev_bev_exists=True 传递时序特征
  根因：BEVFormer 代码硬编码 prev_bev_exists=False
  解决：仅使用单帧推理，放弃时序特征

问题 4.7：检测置信度偏低（Domain Gap）
  现象：Baseline 检测置信度集中在 0.14-0.20（score_thr 需设为 0.05 才有足够检测框）
  根因：nuScenes 预训练模型在 CARLA 域上的 Domain Gap + BEVFormer-tiny 容量有限
  影响：攻击效果可能被高估（相对增幅大，但绝对值小）
  缓解：以相对变化量（DDR/SDR）而非绝对值评估攻击效果

问题 4.8：BEV 特征监控器对图像空间攻击检测率为 0%
  现象：Phase 2 实验表明 BEV L2 ~0.003 远低于阈值 0.027718
  结论：攻击效果完全通过检测头实现，非特征空间漂移
  意义：BEV 编码器鲁棒（余弦自相似度 = 1.0），检测头脆弱
  影响：Phase 4 防御机制需从检测头异常入手，而非 BEV 特征监控

五、WSL 与跨平台环境问题
================================================================================

问题 5.1：WSL 后台进程管理不稳定
  现象：nohup、setsid、screen 均无法保持后台进程
  根因：WSL 2 进程管理与 Windows 会话绑定
  解决：使用前台终端运行长时间实验

问题 5.2：WSL 实例多次失败后卡死
  现象：CARLA 服务端异常导致 WSL 客户端挂起
  解决：wsl --terminate Ubuntu-22.04 重启 WSL 实例
  预防：每 5 路线保存一次检查点

问题 5.3：PyTorch 2.x 与 mmcv 1.4.0 不兼容
  现象：在 PyTorch 2.5.1+cu121 环境中安装 mmcv-full 1.4.0 编译失败
  根因：mmcv-full 1.4.0 仅支持 PyTorch <= 1.13
  解决：创建独立虚拟环境 ~/bevformer-env，降级到 PyTorch 1.11.0+cu117 + mmcv-full 1.4.8

问题 5.4：Windows PowerShell 中文编码问题
  现象：PowerShell 默认 GBK 编码无法正确处理中文路径和 emoji 字符
  报错：UnicodeEncodeError: 'gbk' codec can't encode character
  解决：跨平台脚本使用 ASCII 标记替代 Unicode 字符（[PASS] 替代 ✅，[FAIL] 替代 ❌）
  文件操作：使用 Write 工具 + Bash 复制解决中文路径问题

问题 5.5：Windows-WSL 脚本版本漂移
  现象：Windows 侧修改脚本后未同步至 WSL，导致实验数据不一致
  解决：建立 md5 核对纪律 -- 每次采集前执行 md5sum 确保 Windows-WSL 一致
  流程：修改 -> cp 至 WSL -> md5 核对 -> git commit

问题 5.6：pip 多源安装时的索引源选择问题
  现象：同时使用 --index-url 指定单一索引时，pip 只从该索引查找所有包
  根因：carla 包不在 PyTorch CUDA 源上
  解决：使用 --extra-index-url 或分两次安装（先 PyPI 后 PyTorch 专用源）
  经验：国内用户使用清华源 https://pypi.tuna.tsinghua.edu.cn/simple 提速

六、同步模式与时序问题
================================================================================

问题 6.1：每路线切换同步模式导致状态机混乱
  现象：每条路线开始时启用同步、结束时禁用，导致摄像头回调超时
  根因：多次 apply_settings 累积 RPC 开销，曾导致服务端挂死
  解决：整轮实验单一同步模式，禁止每路线切换
  实现：spawn -> enable_sync -> route_loop -> disable_sync -> cleanup

问题 6.2：在线模式前几帧为预热期被跳过
  现象：20 帧中仅处理 14 帧（前 5-6 帧为预热期）
  根因：摄像头回调需要时间就绪，预热期数据不完整
  解决：增加预热帧到 8-10 帧；增加 --num-frames 到 50+ 改善有效数据量

问题 6.3：帧丢失（部分路线采集 193-199 帧而非完整 200 帧）
  现象：部分帧因摄像头数据延迟或卡死自愈传送而丢失
  影响：统计轻微偏差（<5%）
  缓解：已实现断点续采（--start-route-id），可补采缺失帧

七、数据采集与实验设计问题
================================================================================

问题 7.1：检测数量分布严重右偏（长尾特性）
  现象：Baseline Det Count 分布非正态，均值不能代表典型值
  解决：统计方法从 mean +/- std 改为 median +/- IQR
  应用：analyze_collapse_points.py 全部使用 median/IQR

问题 7.2：攻击效果场景依赖性强
  现象：R3/R6/R9 攻击效果放大 10 倍（Det Count 50+），其他路线效果有限
  根因：几何/光照条件与 patch 扰动产生共振
  影响：攻击成功率不稳定，难以泛化
  缓解：Phase 3 需考虑场景多样性，报告分路线结果

问题 7.3：断点续扫参数遗漏
  现象：用户未加 --resume 参数导致实验从头开始
  解决：在文档中强调显式添加 --resume 参数
  实现：collapse_point_scanner.py 的 scan_batch() 支持 resume 参数

问题 7.4：BEVFormer 检测框恒定 300 个
  现象：离线和在线推理中检测数量恒为 300
  根因：BEVFormer-tiny 的 num_pred 参数设为 300（固定输出数量）
  影响：Det Count 指标需要配合置信度阈值使用才有意义

问题 7.5：h1_quick 快速验证模式的时间-精度权衡
  配置：3 路线 x 100 帧 = 7200 帧/条件（原 5x200=24000）
  原因：GPU 资源受限，需避免长时间占用导致服务退化
  效果：时间减少 42%（~2.4h -> ~1.4h），足以定位崩溃点范围
  局限：统计精度降低，关键发现需用完整方案验证

八、代码架构与工程问题
================================================================================

问题 8.1：collect_attack.py 的 setup_tesla_cameras 函数名错误
  现象：导入时找不到 spawn_tesla_cameras 函数
  根因：脚本中使用了错误的函数名
  解决：修正为 spawn_tesla_cameras，并修正参数顺序 (vehicle, world)

问题 8.2：attack_configs.py 中 patch_frac 最小值约束缺失
  现象：intensity=0 导致无攻击效果的空白条件
  解决：将 patch_frac 最小值约束设为 [0.05, 0.5]，intensity=0 替换为 0.05 作为基线

问题 8.3：Tesla 摄像头映射左右不对称
  现象：TESLA_TO_NUSCENES['CAM_BACK_RIGHT'] = 'side_front_right' 左右命名不对称
  状态：已识别但未完全解决，需用户确认口径

问题 8.4：collapse_point_scanner.py 与 collect_attack.py 代码重复
  现象：帧循环逻辑在两个脚本中重复实现
  解决：collapse_point_scanner.py 直接 import collect_attack.py 的函数
  复用函数：run_one_route_reuse, define_routes, camera_callback_with_name, compute_route_summary

九、失败方案记录（已验证不可行）
================================================================================

9.1 全局 euler_to_rotation yaw 取反
    失败原因：前视摄像头 lidar2cam 矩阵被错误修改
    替代方案：仅对 |yaw|>=45° 条件取反

9.2 同步模式下 spawn 摄像头
    失败原因：tick-spawn 死锁
    替代方案：异步 spawn 后再启用同步

9.3 每帧清空 frame buffer
    失败原因：异步回调来不及写入数据
    替代方案：累积模式保留最新帧

9.4 PyTorch 2.x + mmcv 1.4.0
    失败原因：mmcv-full 1.4.0 仅支持 PyTorch <= 1.13
    替代方案：独立 venv + PyTorch 1.11.0

9.5 world.load_world() 重载地图
    失败原因：耗时且导致 CARLA 卡死
    替代方案：client.get_world() 获取当前世界

9.6 TrafficManager.exe 独立进程
    失败原因：CARLA 0.9.16 无独立 TM 可执行文件
    替代方案：Python API 内置 TM

9.7 每路线切换同步模式
    失败原因：状态机混乱 + RPC 累积开销
    替代方案：整轮单一同步模式

9.8 摄像头回调重复 attach
    失败原因：重复 attach 导致 CARLA 超时
    替代方案：main() 中 attach 一次，跨路线共享

9.9 BEV 时序缓存启用
    失败原因：BEVFormer 硬编码 prev_bev_exists=False
    替代方案：仅使用单帧推理

9.10 CARLA 低画质模式解决 VRAM 瓶颈
     失败原因：仅减少 CARLA 渲染显存（786->224MB），总 VRAM 仍 95%
     替代方案：降低摄像头分辨率 1280x960 -> 640x480

9.11 WSL 后台进程管理（nohup/screen/setsid）
     失败原因：WSL 2 进程管理与 Windows 会话绑定
     替代方案：前台终端运行

================================================================================
附录：关键经验总结
================================================================================

1. 8GB VRAM 设备的摄像头分辨率上限为 640x480
2. CARLA 混合部署（Windows 服务端 + WSL 客户端）可降低单侧资源压力
3. 跨平台脚本必须使用 ASCII 标记，避免 emoji 和中文
4. 每次实验前必须 md5 核对 Windows-WSL 脚本一致性
5. 统计方法应使用 median +/- IQR（检测数量分布严重右偏）
6. 整轮实验保持单一同步模式，禁止中途切换
7. 摄像头回调只 attach 一次，frame_buffer 跨路线共享
8. 长时间实验必须实现断点续采/续扫机制
9. BEV 编码器对图像空间攻击鲁棒，防御机制应从检测头异常入手
10. 攻击效果评估使用相对变化量（DDR/SDR），不依赖绝对值
